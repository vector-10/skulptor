* Handoff doc research (what the designer's spec must contain). No official Anthropic doc on the Claude Design bundle; third party write ups say it holds the design files, a README with build instructions, the chat, and (per one source) component structure, the tokens actually used, layout hierarchy and assets ([claudefa.st](https://claudefa.st/blog/guide/mechanics/claude-design-handoff), [flowpoint](https://flowpoint.ai/blog/claude-design-to-claude-code), [DEV post by bilelsalemdev](https://dev.to/bilelsalemdev/from-prompt-to-pull-request-using-claude-design-claude-code-and-github-together-3m00)). Their claim: the builder matches because it gets structure, not pixels to guess from.
  * Google's DESIGN.md (from Stitch, Apache 2.0, alpha): YAML front matter with tokens (colors, typography, spacing, rounding, components) plus Markdown sections Overview, Colors, Typography, Layout, Elevation & Depth, Shapes, Components, Do's and Don'ts ([the-decoder](https://the-decoder.com/googles-open-source-design-md-gives-ai-agents-a-prompt-ready-blueprint-for-brand-consistent-design/), [dsebastien](https://www.dsebastien.net/design-md-specification/), repo `google-labs-code/design.md`). Open and tool neutral, so a good base. Credit it if used.
  * A full handoff also needs (Mowgli, a vendor, so biased: [article](https://mowgli.ai/blog/design-handoff-to-coding-agents-2026)): screen inventory, states, behavior, exact copy, assets, agent rules, one source of truth. Failure modes: screenshots alone make the builder guess and drift generic; tokens alone give no layout or copy; using the running app as the reference leaves nothing to compare against. Tips: builder uses tokens, never raw hex; builder lists every value it had to guess before coding.
  * Our spec template, proposed: (1) direction: subject's world, signature moment; (2) tokens in DESIGN.md style YAML; (3) layout per section for desktop and mobile with proportions (targets Test 6 dead space); (4) exact copy, facts only from the prompt; (5) components and states (hover, focus, closed day); (6) assets with source, license, local fonts; (7) do's and don'ts incl. the 5 default looks. * Real Claude Design handoff studied (user's own portfolio, `~/Downloads/Portfolio Rebuild Discussion/design_handoff_portfolio/`, not in repo). It has 3 layers, not just a doc:

  3. `screenshots/*.png` at 1485px: declared "the visual source of truth where the README and the HTML disagree". Plus `tokens.css` ready to paste and example content files.

An explicit order of truth (screenshot > HTML > README) and an acceptance checklist make it checkable, which also gives the critic a target.

* Skill writing tips from Anthropic ([best practices](https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices), [engineering post](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills) by Barry Zhang, Keith Lazuka, Mahesh Murag). What we use:
  * Concise: only write what the model doesn't already know.
  * Description in third person, says what it does and when to use it, with trigger words.
  * Low freedom for fragile steps (run the screenshot script exactly), high freedom for design choices.
  * Give a checklist the agent copies and ticks off. This also tracks the round count.
  * Feedback loop: validate, fix, repeat. Only move on when it passes.
  * One concrete example works better than a description (add one example critique).
  * One word per idea: always "issue", "round", "brief".
  * Evaluations first: at least 3 test tasks, compare against a baseline without the skill. Test on every model we use (DeepSeek, GLM).
  * "Claude A writes, Claude B tests": Claude Code helps write the skill, R-CLI uses it, we feed what goes wrong back in. This is our setup.

* Skill format research (redone, the Oct 14 version was never saved):
  * Format follows the open [Agent Skills spec](https://agentskills.io/specification): a folder with `SKILL.md`, YAML frontmatter with `name` (lowercase, hyphens, must match the folder name) and `description` (what it does and when to use it, max 1024 chars), then Markdown instructions. Keep it under 500 lines. Extra files can go in `scripts/`, `references/` and `assets/`, linked by relative path.
  * R-CLI ([skills docs](https://docs.backboard.io/cli/skills)): repo skills in `.agents/skills/<name>/SKILL.md`, found by walking up from the working folder to the repo root, so a skill at the Skulptor repo root works when R-CLI runs in `test-app/`. Personal skills go in `~/.agents/skills/`. The repo one wins if names clash.

Shell commands ask for permission first in the default mode. R-CLI sends images to `deepseek/deepseek-v4.1-flash` (it only blocks a short list of older models).
  * R-CLI also has a `/cua` computer use tool that takes screenshots. Not needed for now.
  * R-CLI is open source, MIT license ([GitHub](https://github.com/Backboard-io/Backboard-R-CLI)). Credit it in the README.
